## v0.42.4 两条修复返工（2026-10-04）
用户复测：v0.42.3 那两条修复**都没生效**。两次都栽在"改的那一层不是真正生效的那一层"。

### 真因
- **图片靠边**：`ImageBubble` 内部 `horizontalAlignment` 是对的，但它的外层
  `Box(Modifier.fillMaxWidth())` 用**默认 `contentAlignment = TopStart`**，
  整块无条件贴左上。→ **凡是"内部对齐了但视觉没变"，先往上找一层容器的
  `contentAlignment` / `horizontalArrangement`**：父容器摆子节点，子节点自己说了不算。
- **输入框上弹**：真因 = **`ime` 与 `navigationBars` 的更新时序错位**。
  adjustResize + edgeToEdge 下键盘收起：ime 先降 0（输入栏掉到底），
  紧接 navigationBars 从 0 恢复到 48dp（键盘可见时被 ime 吸收）又把它顶上去。
  那 48dp 来自外层 `AdaptiveScreen.navigationBarsPadding()`，冻 ime 根本管不到。
  → **键盘避让绝不能两层各管一半**，两个 inset 各自变化就会打架。

### 定稿方案
- 图片：外层 Box 也按发送方切 `contentAlignment`（用户 CenterEnd / AI CenterStart）。
- 键盘：合并成单一量 `bottomInset = max(ime.getBottom(), navigationBars.getBottom())`，
  键盘可见 = 键盘高度、收起 = 导航条高度，**单次连续无跳变** + 220ms EaseOutExpo 下落。
  配套 `AdaptiveScreen` / `AdaptiveSplitScreen` 新增 `applyNavigationBarsPadding`（默认 true），
  **只有 chat 路由与双栏右栏传 false**。
- 回归门禁：`render23ImageBubbleSides` 加**几何断言**（图注中心 x vs 版心中线），
  这类"静默跑偏"以后由测试直接拦下。

### 验证
- 215 项测试 0 失败；截图 `44-image-sides` 已亲眼确认：蓝图靠右+图注右对齐、紫图靠左+图注左对齐。
- AGENTS.md/CHANGELOG 里 v0.42.3 的两条错误结论已就地标注「已被 v0.42.4 推翻」，不要只删不标。

## v0.43.1 返工（用户真机试用 v0.43.0 后提 9 条反馈）

### 本轮最大的发现：语音链路一直是死的
v0.43.0 以为语音能用，实际上有**两个独立死结**，用户看到的现象是
「AI 知道是语音，但不知道里面说了什么」：
1. **格式错**：`SpeechRecognizer.EXTRA_AUDIO_SOURCE` 的文件输入**只吃未压缩 PCM**，

   注意 `MediaRecorder.OutputFormat.WAV` 在 compileSdk 35 里是 **hidden 常量**，
   直接引用 `Unresolved reference`，必须写数值 `6`。
2. **抢麦克风**：`LiveSession`（录制期并行实时识别）和 `MediaRecorder` 同时开麦，
   两边都拿不到音频。→ **整条删除**，统一"先录完、再识别"。

  （`mutableStateListOf<Long>` 记 id），放气泡内部会随滚动回收丢。
- 输入框**高度恒定**（原来空态占位与 BasicTextField 内边距不一致 → 一输入就变矮）。

## v0.43.1 真机第二轮返工（同日，用户 4 条反馈，要求全部修好才交付）

用户原话：「1无后台进入app时卡顿，先显示新建人设然后对话列表才出现，2点击录音键后按按住说话显示启动失败，
发不了语音，3点击输入框唤起键盘后再点击返回只有键盘返回了，输入框还停留在中间，此时再点击表情就变成了
一大片空白，4返回对话列表的时候，先显示底下的tab栏，输入框往上跳，然后才和上面的AI头像栏一起退出」
+ 「你必须完全做好了，完全验证没问题才能交给我，不要拿没修好的给我，并且每个问题都要修」。

### 四条根因与修法

1. **冷启动闪「新建人设」** = 列表只有「空 / 非空」两态，`rows` 初值就是 `emptyList()`。
   引入 `ChatListState(rows, loaded)` 三态（骨架屏 / 新建入口 / 列表）；
   `loaded` **从 rows 派生**（`rows.map { ChatListState(it, loaded = true) }`）。
   ⚠️ **绝不能另发一条 `observePersonas().first()` 去探测就绪**：会与主 `combine`
   争抢 Room 共享 query executor，把列表首值堵死（两个既有单测 60s 超时），
   且 `runTest` 报 `UncompletedCoroutinesError`。与 MEMORY 里 Application.onCreate 的教训同源。

2. **录音启动失败** = `setOutputFormat(6)`(WAV) + `AudioEncoder.DEFAULT` 在小米 ROM 上
   `prepare()` 抛异常，而旧代码 `catch (e: Exception) { false }` **静默吞掉异常**。
   改成 **WAV → MPEG_4/AAC 回退链**（第一组 `prepare()` 成功即采用），
   异常 `Log.e` + 原因记进 `VoiceRecorder.lastError`，提示语带上真实原因。

3. **键盘返回后输入框停在中间 / 再点表情大空白** = 三个叠加原因：
   ① 底部避让只看 `panel != 0`，而点表情那一瞬间 panel 还是 0、ime 还是键盘高度
      → 输入栏被残留高度顶着、面板又在下面展开；
   ② 四条入口（语音键 / 表情键 / 加号键 / 输入框聚焦）各写一份 hide/show，
      漏一处就留下「键盘还开着 + 面板也开着」的窗口期；
   ③ `BackHandler` 面板分支里多余的 `keyboardController.hide()` 会钻空子，
      把用户刚唤起的键盘又按下去。
   正解 = 新增 **`OUTPUT_SWITCH_QUIET_MS = 280ms` 静默期** +
   **所有入口收敛到 `switchOutputMode(nextPanel, nextVoice, showKeyboard)`**；
   静默期内底部避让归零，并立刻放开单调收敛的下界（不等 120ms）。

4. **返回时底栏先冒出来、输入框上跳** = `currentBackStackEntryAsState()` 在
   `popBackStack()` **那一刻**就切回 home，而退场动画要跑 420ms；
   这期间底栏已渲染、Scaffold 的 `innerPadding` 随之加大，
   把正在滑出的页面往上挤。
   正解 = **底栏显隐也走 `AnimatedVisibility`**（进场延迟到页面滑走之后、退场立刻开始），
   并抽 `PUSH_TRANSITION_MS = 420` 让所有 push 路由与底栏共用同一时长。

## v0.43.1 真机第三轮返工（2 条反馈，同版本内完成）

用户反馈：①「点表情再点输入框键盘会把输入框挡住」；②「发语音 AI 还是识别不了什么原因」。

### 根因与修法

1. **点表情再点输入框，键盘挡住输入框** = 上一轮加的「输出形态切换静默期」**修过头了**。
   静默期的语义是「这一轮不要键盘了，别再用键盘高度顶输入栏」，
   但我把它套在了**所有**形态切换上 —— 包括"要弹键盘"的那种。
   于是点输入框时底部避让被压成导航条高度，而键盘正往上弹、已经盖住输入栏。
   正解 = `switchOutputMode()` 里**判方向**：
   `keyboardWanted = showKeyboard && nextPanel == 0 && !nextVoice`；
   `outputSwitchAt = if (keyboardWanted) 0L else System.currentTimeMillis()`
   —— 要弹键盘时静默期**置 0 = 没有静默**，立刻跟随真实 `ime` 高度。
   教训：**给某个过渡打补丁时，必须问一句"反方向会不会被误伤"。**

2. **语音识别不了（真根因）** = `SpeechRecognizer.EXTRA_AUDIO_SOURCE`（API 31+）的
   "文件输入"能力**在国产 ROM 上普遍不生效**。小米等定制系统的识别服务**只监听实时麦克风**，
   喂它音频文件路径等于没喂：`onResults` 不回调、`onError` 也可能不给，
   最后 `withTimeoutOrNull` 走满 20s 返回 null。
   **上一轮把录音格式换成 WAV/PCM 是对的，但救不了这条路 —— 对方压根不读文件。**
   正解 = **三级级联**（`SpeechToText.transcribe`）：
   ① **云端 Whisper 主力**：新增 `OpenAiClient.transcribe()` 走
      `POST {base}/audio/transcriptions`（multipart `file` + `model=whisper-1` + `language`），
      复用用户已配好的 AI 接口 baseUrl/apiKey，零额外配置；
      MIME 按扩展名推（wav→audio/wav、m4a/mp4/aac→audio/mp4、mp3→audio/mpeg）；
      响应先试 JSON 的 `text`、失败当纯文本（兼容中转商）；60s 超时，失败安静 null。
      `ChatViewModel.cloudTranscribe(file)` 负责取配置并调用。
   ② 系统识别器喂文件 —— 兜底。
   ③ 都失败 → null（语音照发、content 空）。
   **关键设计：`cloudTranscribe` 由调用方以 `suspend (File) -> String?` 注入** ——
   `SpeechToText` 保持纯逻辑对象，不知道 API 配置从哪来（可测试性也靠它）。

3. **补 `<queries><intent android:name="android.speech.RecognitionService"/></queries>`**：
   Android 11+ 的包可见性**同样管 `SpeechRecognizer`**，不声明会让
   `isRecognitionAvailable()` 恒为 false。已补进 `AndroidManifest.xml`。

### 踩到的两个新坑

- **`android.util.Log` 在纯 JVM 单测里未 mock**：`OpenAiClient.transcribe` 里直接
  `android.util.Log.w` 会抛 `Method w in android.util.Log not mocked`。
  → 用 `runCatching { Log.w(...) }` 包住（`logWarn()` 辅助）。
- **`RuntimeEnvironment.getApplication()` 在无 runner 的纯 JVM 类里返回 null** →
  NPE。Robolectric 测试必须 `@RunWith(RobolectricTestRunner::class)` +
  `@Config(sdk = [34])` + `ApplicationProvider.getApplicationContext()`。
  首次跑测试时 `SpeechToTextTest` 7 条全 NPE，就是踩了这个。
