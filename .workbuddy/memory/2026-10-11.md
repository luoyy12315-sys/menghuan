## 修「人设回复看不到上下文」（v0.95，源码完成，未编译）

### 根因（v0.86.0 埋的算术 bug）
`ChatViewModel` 历史预算公式 `窗口 − systemPrompt 字数 − OUTPUT_RESERVE_CHARS(8,000)`
是 **20 万字窗口时代**的算法；v0.86.0 把默认窗口降到 12,000 时公式没重审，
**8,000 余量吃掉窗口的 2/3**：
- 典型人设（固定协议段 ≈1,850 字 + 设定词/档案 ≈1-2.5k）：历史只剩 **~500 字**（三四条消息）；
- 滚动摘要尾巴拼在 system 尾部 → 摘要越长 system 越长 → 预算越早 ≤0 → **只发最新一条**；
- 内置应用助手（手册 2.9 万字）恒为负 → 永远零历史；
- 连锁踩坑：`SummaryEngine` 按**整个** 12,000 判「掉出窗口」，被多减的那段消息
  **既不进历史也不进摘要 → 静默蒸发**（v0.82.0 注释警告过、v0.86.0 修过一次的坑，被这个减法重新挖开）。
- 教训（再次应验「看到常量先问它凭什么」）：降默认值时必须重审依附于旧量级的所有常量/公式。

### 修法（用户拍板：纯历史口径）
`budget = window`，不再减 systemPrompt 和输出余量；`OUTPUT_RESERVE_CHARS` 删除。
依据：① 设置项标签叫「记住最近多少字」，手册也写「最近这些字数的对话会原样带着走」
——**承诺本来就是纯历史，是代码没兑现**（所以手册零改动）；② 12,000 远低于任何现役
模型真实窗口，「防 400」不靠减法；③ 改完后历史与摘要读的就是同一个窗口，蒸发缝自动闭合，
`SummaryEngine` 一行不用动。
- 改动只在 `ChatViewModel.kt`：预算公式 + 删常量 + 三处过时注释（"20 万字"残留）；
  `HISTORY_CHAR_BUDGET` 文档补「口径 = 纯历史字数（v0.95）」一节。
- 测试：无断言钉旧公式（公式当时是内联的、没进纯函数），`HistoryBudgetTest` 等全部现有断言保持有效。
- ⚠️ 成本提示：修好后每轮真的会带足 12,000 字历史（以前只带几百字），每轮 token 消耗
  升到设置项承诺的水平 —— 手册早已如实描述「填得大 = 每轮重发花更多钱」。
- 未编译未跑测试（按规则等点名）。

## 给「人设心情」接上输入端（v0.98.0，源码完成，未编译未跑测试）

### 用户报的问题

### 根因（三层叠加，第一层是真 bug）
1. **valence / arousal 没有输入源**：`CompanionLogic.applyDelta()`（设计里"用户倾诉/吵架→落轴"的入口）
   **全工程零调用点（死代码）**；只剩 `tick()`（把 valence 往基准 −0.05 拽 / `connection≥0.6` 时锁住）
   与 `onUserMessage()`（不碰 valence）两条写路径 → 两根轴恒为常数。
2. **v0.77.0 徽标只读 valence** → 唯二真在动的轴（connection/pride）界面上零体现。
3. 写入时机本来就稀少（只在主动触发 tick / 用户发消息时落盘）。
→ `moodOf` 九个情绪簇只有「情绪平平」可达，心情计恒半格。
**归入 MEMORY 老教训：参数/函数写好了，消费方不存在**（与 v0.86.0 那两个真 bug 同源）。
另：用户一度以为「心情是随机的」→ 澄清：**机制是确定性的、零 Random**；问题是"没输入→冻结"，不是"随机地不一样"。

### 档案是什么
`profile_facts` 表筛出来的 `- key：value`。**两种来源混一张表、都注入**：
`personaId=0` 用户基础档案 / `personaId>0` 该角色聊出来的记忆。
- 筛法 `MemoryScope.visible(all, personaId, sharedReadable)`：自己的 + 基础档案（开关默认开）；
  `core` 置顶 → 按 `id`。**刻意不用 updatedAt** 排序（前缀稳定，§零.9）。
- 位置：聊天链 / 实时通话 → **system prompt**（套可编辑 `profilePreamble`）；
  主动关心 / 定时消息 / 来电开场白 → **userContext**（只给 `【用户档案】` 标签，**不套 preamble**）。

  **实时通话无上限**（`facts.forEach`，连 `.take()` 都没有）。

### 第二问的答案：上限掐的不是「记不记得」
存储不封顶；被 `take(30)` 折叠的条目**仍在召回池里** —— `take` 只发生在拼接 system prompt 处，
召回池是 `MemoryScope.visible()` 全量（`ChatViewModel:2321/2335`）。每轮以「用户最后一条消息」为 query 搜
（词法 bigram ≥60 + 可选语义 ≥0.75），top 3 贴到最后一条用户消息；归档条目高分（≥80）召回**当场复活**、
命中即 `touchRecalled`（免 90 天自动归档）。
→ 常驻 30 =「一直在场」，其余 =「聊到就想起」。封顶三条理由：① 全量罗列稀释注意力，反而更健忘；
② 档案**单调增长** + 无状态 API 每轮全量重发 → 不封顶成本随时间线性涨；③ 前缀变长稀释缓存价值。

## 手机 Agent 实现走查（用户问「现在的 agent 怎么实现的」）

代码全在 `com.menghuan.app.agent`（6 文件 ≈700 行）+ `notify/AgentNotifier` + `ui/tasks/AgentSheet`。
**路线 = 无障碍服务读屏 + LLM 决策 + 无障碍手势执行**（不是 ADB / root / 投屏）。

- `AgentAccessibilityService`：单例 + `windowTick`（窗口变化计数）+ 悬浮「■ 停止」（TYPE_ACCESSIBILITY_OVERLAY，免悬浮窗权限）
- `ScreenState`：BFS 把节点树压成**编号元素清单**（DroidRun 式），上限 `MAX_ELEMENTS=40` / 遍历 600 节点
- `AgentPrompts`：决策 system prompt（5 种 JSON 动作）+ 宽松解析 + 敏感词表 + `[操作手机:…]` 标记协议
- `ActionExecutor`：tap/swipe 走 `dispatchGesture`、输入走 `ACTION_SET_TEXT`、back/home 走 `performGlobalAction`
- `AgentLoop`：主循环（最多 15 步；解析失败重试 1 次；连续两步同动作判卡住；`waitWindowStable` 静默 900ms/超时 2.5s）
- `AgentRunner`：Idle/Running/Finished 状态机，`autoConfirm` 决定敏感动作是否打断

**两个入口**：① 对话内 `[操作手机:目标]`（`autoConfirm=true`、应用级 scope、结果落库成 🤖 消息）；
② 任务页 ▶（`AgentSheet`，走 UI 敏感确认、VM scope＝离开页面即取消）。

**走查发现的三个薄弱点（未改，仅记录）**
1. **元素定位只靠屏幕坐标中心**：`ActionExecutor.findByCenter` 拿快照时的 centerX/Y 去当前窗口回找节点，
   快照与执行之间页面一变就找不到（返回 null → 记为执行失败）。没有节点 id / 时间戳校验。
2. **失败动作不计入「卡住」判定**：`sameActionStreak` 只在**成功**时比较，
   一个反复失败的动作不会触发"卡住"，只能靠 `AgentPrompts.SYSTEM` 规则 4 让模型自己 done（提示词兜底，非代码兜底）。
3. **敏感词围栏只看元素文案**：`isSensitive(element)` 查的是元素的 `text + contentDescription`，
   `text` 动作要输入的 `value` **不参与检查** —— 往标签是「备注」的框里输敏感内容不会被拦。

**成本与隐私（值得跟用户点明）**：每步是一次**独立非流式请求**，prompt 含最多 40 条元素清单 + 最近 8 步历史
→ 15 步 ≈ 15 次对话量。且**屏幕文字（含别的 App 的内容）会发到用户自己配的接口**，
白名单是这方向上唯一的控制手段（手册里「数据只存本机」指的是不上传我们自己的服务器）。

## 手机 Agent 现方案痛点调研（GitHub 调研，未动代码）

用户报两个痛点：**① 每次操作手机都要去设置里开无障碍；② 容易卡、慢**。上 GitHub / 网络调研结论：

### 痛点 ① 的根因：不是 Android 的必然行为，是「被杀 + 没有自愈」
- 无障碍服务**正常情况下重启后仍保留**；会被关掉的原因是：App 被强行停止 / 国产 ROM 清理 / 服务崩溃后没重挂 / 电池优化杀进程。
- 行业解法（DroidRun 官方文档原文）：`_recover_portal` —— 读状态连续失败 5 次后**自动重启无障碍服务**；外层是 1s→10s 指数退避、7 次重试。**我们完全没有自愈，也没有前台服务保活。**
- 三个可选后端（按「省事程度」排）：
  - **Dhizuku**（`iamr0s/Dhizuku`，Device Owner）：**一次激活，重启不失效**。代价：激活时必须**删光所有账号 + 系统分身/双开**，OPPO 等需自行签名；支持的 App 生态小。
  - **Shizuku**（`shizuku.rikka.app`）：uid=2000 的 ADB 权限，用无线调试激活（Android 11+，**不需要电脑**）。**重启后要重新激活**。生态极大（`awesome-shizuku` 清单里大批同类项目）。
  - **自愈 + 保活**（纯本地、成本最低）：前台服务常驻 + 电池白名单引导 + `isEnabledInSettings()==false` 时弹条深链跳设置 + 读屏失败自动重挂。
- ⚠️ 关键事实：**Shizuku 也逃不过"重启要重激活"**，Dhizuku 才真正免了这一步但一次性代价很大。所以"最小摩擦"其实靠**自愈保活**。

### 痛点 ② 的根因：四个叠加
1. **读屏慢且会卡**：a11y 树几千节点，我们 BFS 600 个（DroidRun 官方也承认 "accessibility service stutters"）。
2. **每步一次独立 LLM 请求**（最大延迟源）：15 步 = 15 次往返、非流式、每轮全量重发 40 条元素 + 8 步历史。
3. **无条件 sleep**：`waitWindowStable` 静默 900ms / 最长 2.5s。
4. **坐标定位**→页面一变就失败→重试→更慢（对应走查薄弱点 1）。
5. 次生：非流式，用户看不到中间状态 → **感知上更慢**。

### 我给出的建议顺序（已答复用户，等点名才动）
1. **保活 + 自愈 + 一键跳设置**（纯本地，直接治痛点 ①）
2. **元素裁剪 + 稳定定位**：只留可见/≥5px/可交互节点（DroidRun ConciseFilter）、改用 `viewIdResourceName` 代替坐标、元素带快照时间戳（直接治"卡住"）

6. （大改）观测层换**混合输入**；若用户 API 不支持视觉，则内置端侧小模型
   —— 我们构建**本来就是 arm64-only + onnx `noCompress` + sherpa JNI**，塞端侧模型的"路"已经通了一半。

⚠️ 1-3 是**纯本地改动，不依赖用户装 Shizuku 或换模型**，建议先做；4-6 属第二步。

**已核实（grep 证据）**：全 `app/src/main` 下 `startForeground|foregroundServiceType|FOREGROUND_SERVICE|setForeground`
**零命中** —— 即项目里**一个前台服务都没有**，`AgentAccessibilityService` 只是系统绑定的无障碍服务，
没有任何保活手段。所以"无障碍被关"是**结构性必然**而非偶发。另核实该服务本体（108 行）：
只有 `instance` / `windowTick` / `isRunning()` / `isEnabledInSettings()` / 悬浮停止按钮，
**无 `onServiceConnected` 之外的任何恢复逻辑**（DroidRun 的 `_recover_portal` 对应物完全缺失）。

**用户追问「哪种更便捷/快/代价少」时给出的判断**：不存在单条路三维全赢。
- 「便捷 + 代价低」最优 = **本地四件套**（保活/自愈/元素裁剪/失败止损）→ 用户零操作、零新依赖。
- 「快速」最优 = **动作脚本缓存**（重复任务 15 次 LLM 往返 → 0）。
- 两者不冲突，可一起做，且都不加依赖 → **这就是推荐组合**。
- **Shizuku 不是"便捷解"**：它只是把"每天进设置开无障碍"换成"每周重启后激活一次 Shizuku"，
  摩擦形式变了；它真正的价值是**执行更快更稳 + 为视觉铺路**，应做成**可选后端**而非强制。
- Dhizuku 对普通用户直接排除（要清光账号 + 系统分身）。
- 视觉模型三个维度里只在"代价"上崩（包体/工程/依赖用户 API 是否支持传图）。
- ⚠️ 诚实局限：**代码无法自动重新打开无障碍服务**（Android 安全限制），
  保活只能"从源头减少被关"，关了之后只能靠入口处一键深链跳设置页兜底。

## 手机 Agent 步进开销：**纠正我上一轮的错误归因**（读码后）

上一轮我说「每步把 40 条元素 + 8 步历史全量重发是最大延迟源」——**这句话一半是错的**，已当面向用户更正：

- **8 步历史不是重发完整清单**：`AgentLoop` 的 `history` 存的是 `execute()` 返回的**短描述串**
  （如 `"点击 [3] 保存"` / `"输入 [4] = xxx"`，见 `AgentLoop.kt:146,156`），8 条约 80 token。**不是大头。**
- **元素清单必须每步重发**：无状态 API，模型不看当前屏就没法决策 → 这是**该层架构的必然成本，不是浪费**。
- **真正的病根是「步数 × 单次往返耗时」**，不是"重发多少字"。

真实延迟账单（15 步）：LLM 往返 15–75s（绝对大头）/ `waitWindowStable` ≥13.5s 纯等待 / 读屏 BFS ~2s。

**可动的地方（按性价比）**
- **A. `AgentLoop.kt:163 waitWindowStable` 无条件等 900ms**：`quietStart` 从函数入口就计时 → **保证最少等 900ms**，
  15 步 ≥13.5s 纯浪费。可改「先等首次 tick 变化 ≤600ms，出现变化后再等静默 400ms，600ms 内无变化直接返回」。
  ⚠️ 属**时序/行为改动**，有"慢 App 提前返回读到旧界面"的风险，**要先问用户**。
- **B. 元素清单瘦身**（`ScreenState.kt:42`）：准入条件是 `clickable || editable || scrollable || hasText` ——
  **`hasText` 会把纯文本装饰节点全放进来**（标题/价格/说明），40 条里可能一半没人点。
  可收紧为「默认只发 clickable/editable，纯文本仅在无可交互元素时兜底」+ 去重（列表里 10 个相同按钮只留 3 个标 `×10`）+ 截断 30→20 字。
- **C. `AgentPrompts.kt:55 userPrompt` 顺序可换**：现在是「目标 → 屏幕 → 历史」。
  屏幕清单**整体替换**、历史**追加式增长** → 把历史**提到屏幕之前**，两次请求的公共前缀能从
  "当前屏幕元素：\n" 一直延伸到**整段历史**，前缀缓存多命中一段。零成本。
  ⚠️ 但若服务商是 OpenAI 那种 **1024 token 一块**的自动缓存，`SYSTEM`（约 175 token）**压根够不到门槛**；
  DeepSeek 的 64 token 粒度吃得到。**判据：看用量页 Agent 这条链的 `cachedPromptTokens` 是不是 0。**
- **D. 重试是「原样重发」**（`AgentLoop.kt:60-63`）：解析失败后**发一遍一模一样的请求**，
  结果多半还是错的 —— 等于花两次钱拿同一个错误答案。应改成重试时**追加一句「上次输出无法解析，只输出 JSON」**。
  这是**真 bug 级浪费**。
- **E. 批量动作**（一次返回 2–3 步）是唯二能把 15 次往返降到 5 次的手段；只在确定性高的连续动作上启用。
- **F. 加「Agent 执行模型」配置项**：每步决策是简单任务，用小/快模型可让延迟近半。
- **G. 流式**：**不能减少总时长**（JSON 必须完整才能执行），只改善"看得见在动" + 可设超时掐断。别把它当提速手段。

**结论**：治本是**减少往返次数**（B/C/D/E/F），A 是最快见效的。已告知用户，等点名。

## 手机 Agent 优化 M2 实施（用户：「直接进 M2」）

**范围 = P0 后半：D 元素瘦身 / E 失败止损 / F 定位稳定 / G 敏感词围栏。** 全程纯本地、无新依赖。

### D 元素清单瘦身（`ScreenState`）
- BFS 采集后统一走**纯函数 `compact()`**（可单测；准入与折叠只有一处实现）：
  ① 准入收紧 → 只留 `clickable || editable || scrollable`，**纯文本节点仅当整屏没有任何可交互元素时才兜底发出**；
  ② 折叠：形状相同（`type + 真实文案`）的成排按钮留前 `REPEAT_KEEP=3`，总数标在第一条上 `×6`；
  ③ `toPrompt` 标签截断 **30 → 20 字**（`LABEL_MAX`），**只影响清单文本**，`UiElement.text/desc` 保持完整
  （`isSensitive` 与日志仍看全文）。
- ⚠️ **两处关键判断（别走回头路）**：**先折叠再截断**（否则成排重复按钮吃光 40 个名额）；**没有真实文案的节点不参与折叠**
  ——`label` 在无文案时会回落成 type，若按 label 折叠，一排纯图标按钮会被折成一个，模型就点错了。
- `snapshot(root, tick)` 新增 tick 参数。

### E 失败动作也计入卡住判定
- 新增 `AgentPrompts.actionSignature(action)`：`tap[3]` / `text[4]` / `swipe[up]`。
- `AgentLoop` 的 streak **从"执行结果描述"改为"动作签名"** → 失败动作首次纳入止损；连续 2 次同类即中止。
  `text` 的**输入内容刻意不进签名**（同一框反复灌、每次都失败就该判卡住）。
- `execute()` 返回类型 `String?` → **`StepOutcome`（Done/Failed + 可读原因）**，失败原因第一次能写进日志与历史。

### F 定位稳定化
- `UiElement` 新增 `viewId`（`viewIdResourceName`）与 `snapTick`；`ActionExecutor.resolve(element, allowCoordinateOnly)`：
  **resourceId 优先**（同 id 多个时取离快照中心最近者 → 列表行共享 id 不串行）→ 坐标兜底。
- ⚠️ **"界面动过没有"必须比窗口 tick，不能比自己的快照序号**：序号只有自己会推进，比它永远相等 = 没校验

## 音色克隆两个用户报障（用户：「只能克隆一个」+「效果也不好」）—— 6 项全改

**用户确认的关键事实**：第二次克隆**上传成功、无任何报错** → 直接指向"服务端收到同名 → 覆盖/视作同一个"。

### 根因（读码 + 官方文档核对，非推测）
1. **`asciiVoiceName` 会撞名**（`VoiceCloner.kt`）：旧实现只把显示名里的 ASCII 抠出来当 `customName`
   （`小美a` / `小明a` → 都变成 `a`；两次都叫 `yuki` 也同一个）→ 服务端同名 → **名单里永远只有一条且不报错**。
   这是"只能克隆一个"的主因。
2. **MiMo 样本文件名固定**（`prepareSample` 落 `${音色名}.wav`，而选样本那刻名字还没填 → 恒为"我的音色.wav"）
   → 第二次把文件覆盖；MiMo 的音色名单**就是该目录里的 .wav** → 按设计只能有一个。
3. **克隆成功后没写本机名单缓存**（只写了显示名 + 设默认）→ 名单唯一来源是 `/audio/voice/list`，
   那次请求失败时刚克隆的在界面上查无此音。
4. **隐藏表只进不出**（`SettingsRepository`）：长按删一条后无任何恢复入口 → 看起来像"少了一个"。
5. **效果不好**：逐字稿是端侧 SenseVoice 自动转的，而它开着 **ITN**（`useInverseTextNormalization = true`），
   会把口语数字改写成阿拉伯数字；官方明写 **"Prompt text must match the prompt audio content"** → 对不上就跑调。
   ⚠️ **不能靠"再开一个 ITN=false 的识别器"解决**：228MB 权重两份 ≈ 500MB，正是 `SherpaAsr` 头注释警告过的
   OOM 场景（且语音栈是铁律保护对象）→ 改为**含数字时 UI 明确提示核对** + 重听样本。
   另外官方对样本的硬要求（单一说话人 / 无 BGM / 音量稳定 / 8~10 秒）我们一条都没校验过 → 只能 UI 明示。

### 改动
- `VoiceCloner.asciiVoiceName(display, stamp = 4 位随机)`：**一律拼唯一后缀**（base 截 40 + 后缀，≤64 字符）；
  测试用固定 stamp 断言，**不依赖随机数**（避免 flaky）。
- `VoiceCloner.prepareSample`：文件名 `${sanitize(name)}_${时间戳}.wav`（唯一）；
  新增 **`normalizePeak`**（只放大不缩小、+12dB 封顶、已够响/全静音原样返回）并在重采样后应用。
- `SettingsRepository.unhideVoice(provider, voiceId)`（隐藏表第一次有了出口）。
- `VoiceLibrarySection`：克隆弹层①顶部改成本官方四条要求②逐字稿在**含数字**时单独警告③新增「▶ 重听样本」
  （复用 `playTtsPreview`，播本地裁剪后的 wav）④上层把 `asciiVoiceName` **只算一次**并复用（否则存进缓存的名字
  与真正上传的不一致）⑤成功后**写进本机名单缓存**；音色页底部新增「查看已隐藏的音色（N）」+ 逐条恢复弹层。
- 测试：`VoiceClonerSampleTest` 新增 4 条（唯一命名 / 峰值归一三态）。
