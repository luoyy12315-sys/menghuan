## v0.84.0：AI 引用任务口径收紧（TaskContext 统一出料）

### 问题
用户点名「AI 聊天时老是时不时提到无关紧要的任务，包括已完成 / 已过时 / 很久之后的」。

### 根因（关键教训）
**不在模型乱说，在宿主喂的料本身没有时间信息**。四条链路各自拼「【最近未完成任务】+ 一串任务名」，
只看 `isDone` 不看 `dueAt`：
- 逾期任务 `isDone == false` → 每次都被列出来（`AiCall`/`ScheduledMessageSender` 甚至只看 `isDone` 全捞）；
- 每日任务跨天 `isDone` 还是旧值（该走 `isEffectivelyDone`）→ 昨天做完的今天又被催；
- 明天/下月到期的和今天该做的混一列，模型随手挑一条。
**光在提示词里写「不要提过期的」没用——料里带着过期任务，模型就有理由提。**

### 做法
新建 `data/TaskContext.kt`（唯一出料口）：按**归属日**分桶 + 附 `DISCIPLINE`。
口径（用户拍板）：今天该做（主，≤8）/ 明天到期（≤4）/ 今天已完成（给名字）/
**逾期只给件数不给名字** / **3 天以后整块不进上下文**。
纪律段写进料旁边（易变上下文），不进 system prompt。

接入四处：`ChatViewModel.taskStatusBlock`、`ProactiveChat`（原「近 7 天未完成」会把已逾期当当话题）、
`AiCall.GREETING_INSTRUCTION`、`ScheduledMessageSender`。
**`PipelineVoiceCallEngine` 刻意不加任务块**——通话是实时对话，每句挂任务块就成了打卡机。

提炼侧同步收紧（用户拍板「一起收紧」）：`ProfileExtractor.DEFAULT_STRATEGY` 第 3 条扩写
（空泛愿望「多喝水」「加油」不许成任务、同名不重复建议、3 天以后不带 date）；
`ExtractionEngine.buildTaskContext()` 并入 `TaskContext.forExtraction()`（以前不给现有任务清单 → 重复建议）。
手册：`AiPrompts` 「3. 任务」段末追加 v0.84.0 补丁（锚点 = 段末「建议会带上到期日期」，全文件唯一）。

### 顺手修的过期断言
`McpClientTest > callTool 文本扁平化`：断言 `contains("\\\"x\\\":1")` 把参数当成"再套一层 JSON 字符串"，
而 `org.json` 序列化 `JSONObject` **内层引号不转义**（实际 `"arguments":{"x":1}`）→ 恒不成立（单跑必红，非 flaky）。
改成断 `"\"x":1"`。**实现没动。** 这条自 v0.82.0 起就在红，上一版全量没跑完所以没暴露。

### 测试基线（补上上一版欠的）

### 1. 动态时间线标清作者
- 用户问「AI 发动态分得清是谁发的吗」。查下来**数据层一直分得清**（`moments.personaId`

### 2. 记忆不再重复
- 用户反馈「AI 的记忆老是重复的」。根因：`ExtractionEngine.runExtract()` **不告诉模型已记过什么**，

- 修法（用户拍板「给模型现有条目名 + 命名规范」，**旧数据不处理**）：
  `ExtractionEngine.buildExistingKeys(personaId)` 读全表走 `MemoryScope.visible`（与注入同口径）
  → **只给 key 不给 value** → 拼「【已经记住的条目名】」段 + 「复用那个名字」；
  `ProfileExtractor.DEFAULT_STRATEGY` 新增第 1.1 条 key 命名规范（2-6 字名词、不带版本感、复用优先）。
- 新测试 `ExtractionEngineTest` 1 项。

## 退出「个人档案」莫名震动（v0.93.0 内修，源码完成）

### 根因
滚轮的"框心"是用 **`boundsInRoot()` 相减**量出来的（`框心 − 排左缘`），而 `boundsInRoot()`
报的是**含祖先变换**的坐标；`ME_PROFILE` 的退场转场是 `pop + scalePop = slideOut + scaleOut(0.96)`
（MainActivity `settingsComposables`）——整页一缩，这个距离被压缩约 `(1-0.96)·W/2 ≈ 7dp`，
**列表却一格没滚** → "离框心最近的那格"凭空挪一格 → tick 震一下。
进场只有 `slideIn`（平移，两值同增同减、差值不变）→ **只有退出才震**，与现象完全对上。
⚠️ 同一记假 tick 还会走 `onEmojiChange` → 档案页是即时落盘的，**震一下 = 头像被存成旁边那个**
（比震动更严重的静默数据错）。

### 修法（两层，都在 `AvatarEmojiWheel.kt`）
1. **框心改用布局量**：新增 `anchorInRowPx()` = `bothSides → rowWidthPx/2`、否则 `frameSizePx/2`
   （`rowWidthPx` 取 `onGloballyPositioned` 的 **`it.size.width`**，不受任何祖先变换影响）。
   `indexAtAnchor()` / `alignOffsetPx()` / 初始定位的 delta 补偿**统一走它**。
   数学上 `框心 = startPad + 格宽/2`，所以排宽变化时也照样抵消 —— 选中格**只由滚动位置决定**。
   `rowLeftX` 已删（grep 0 处）；`anchorX` 保留，只服务每格的 focus 放大（root 坐标前后一致）。
2. **只认真的滚动**：tick 的 `collect` 里记 `lastScroll = (firstVisibleItemIndex, scrollOffset)`，
   滚动位置没变的一发直接丢弃（重新定位后第一发 `lastScroll == null` 照旧认，否则首格不上报）。

### 教训（可复用）
`onGloballyPositioned` + `boundsInRoot()` 的量会**跟着页面转场漂移**；凡是"拿它判定选中/命中"
的逻辑，要么改用 `size`/布局量，要么加一道"数据源真的变了"的闸门。
排查这类"莫名其妙"先列全项目 `performHapticFeedback`（本轮 13 个文件里只有滚轮是**自触发**的，
其余全是点击/长按）。
