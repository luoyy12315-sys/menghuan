## 〇、结论摘要

梦欢在「AI 陪伴 + 学习生活助手」赛道上的完成度**显著高于绝大多数开源同类项目**：自研实时语音管线、主动电话/主动关心/定时消息三件套、Live2D 全链路、无障碍手机操作 Agent、记账/任务/周报生活管理线，这些在 GitHub 上找不到第二个同时具备的开源 App。

最需要补的三块短板，按紧迫度排序：

1. **超长会话的"金鱼脑"** —— 记忆体系已分层完整，但 20 万字预算外的历史是硬截尾蒸发，没有摘要压缩；这是陪伴类产品最伤体验的一点。
2. **token 统计的口径盲区** —— prompt cache 工程做得很专业，但主动关心/语音通话不记账、分模型不记缓存读数，"省了多少钱"用户看不全。
3. **工具生态缺位** —— 无 function calling / MCP，LLM 只能靠文本标记协议办事；这是与 AIRI 等新一代项目最大的代差。

Live2D 是全场最高分项，防御性与完成度都属一流，只剩易用性边角。

## 一、记忆模块评估

### 1.1 现状架构（分层）

| 层 | 实现 | 关键文件 |
|---|---|---|
| 短期上下文 | 全量历史按 20 万字预算从新到旧截尾（`HISTORY_CHAR_BUDGET = 200_000`，对齐服务商半价计费档） | `ChatViewModel.kt:320-338` `selectHistoryByCharBudget` |
| 事实记忆库 | `profile_facts` 表：按人设隔离（v0.70.0 `MemoryScope`）、生命周期六态、AI 添加进待审区（staging）、词法检索召回 | `MemoryScope.kt` `MemoryMarker.kt` |
| 增量提炼 | 每会话消息水位线，攒够 8 条新消息自动提炼 → ProfileFact + 洞察(留20) + 任务建议 | `ExtractionEngine.kt` |
| 回顾沉淀 | AI 洞察、AI 周报（上周数据 + 对话节选 LIMIT 60） | `WeeklyReportGenerator.kt` |
| 召回注入 | 每轮拿用户最新一句做 bigram 词法检索（阈值60取3条），命中记忆作"## 你想起来的事"贴易变上下文 | `ChatViewModel.kt:1897` `memoryRecallBlock` |
| 记忆管理 UI | 「TA 的记忆」页：按人设查看/改生命周期/删除 | `ui/memory/MemoryScreen.kt` |

### 1.2 优点

1. **分层完整且克制**——历史 + 事实库 + 生命周期 + 待审 + 召回 + 提炼 + 周报，机制齐备但不堆砌；`MemoryScope.visible` 按 core 置顶 + id 稳定排序，刻意保护 prompt cache（注释写明"按 updatedAt 排会抖缓存"），工程意识一流。
2. **记忆按人设彻底隔离**——A 角色聊出的"口味=辣"不会串到 B 角色（v0.70.0 修过同名覆盖 bug），基础档案（personaId=0）受共享开关单独控制，语义干净。
3. **提炼是"尽力而为的旁路"**——应用级作用域、失败静默、绝不影响聊天；manual 条目不被 AI 改 source；rejected 条目永久不回。权责清晰。
4. **召回是"宿主主动推"而非"模型发指令"**——不依赖模型自觉发 search 标记，比 Letta 式 agentic 检索更省 token、更可控，适合中小模型。
5. **提炼策略用户可编辑**（`extractionStrategy`），且「AI角色≠用户本人」铁律写进 `ProfileExtractor.FRAMEWORK`。

### 1.3 缺点与改进点

1. **超长会话硬截尾，无摘要压缩（最重要）**——`selectHistoryByCharBudget` 只截不压，聊到 20 万字后旧内容对模型完全蒸发。陪伴场景下"三个月前说过的事"正是用户最在意的。对标：Mem0 的结论"大上下文只是延迟遗忘，不解决遗忘"。
2. **档案全量逐条注入，无上限**——system prompt 里 `- key：value` 逐条全带，只有召回块限 3 条。记忆条目涨到几百条后，前缀变长 → 缓存命中价值被稀释、每轮成本线性上涨。
3. **召回只有词法，无语义**——bigram + ASCII 词对"换个说法"的命中弱（用户说"忌口"，记忆里存"不能吃辣"就召回不到）。 Mem0/Letta/PLUR 的共同结论是 hybrid（向量+BM25+实体）召回显著优于单一信号。
4. **待审区（staging）可能积压**——AI 标记的记忆堆在待审里，若用户不常开记忆页，等于 AI "记不住"。缺少轻量通知/角标引导。
5. **messages 表无裁剪无分页**——唯一无上限增长表；`observeConversation` 全量 ASC 读进内存再清洗截预算（`ChatViewModel.kt:1071`），长会话首读延迟与内存是隐患。
6. **助手手册挤占预算**——215 条 `.replace()` 链产物（v0.38 底稿 + 一路补丁，含整章教程）是助手会话的固定前缀，直接扣减 `HISTORY_CHAR_BUDGET`（`ChatViewModel.kt:1113`），助手会话可用历史被自己的说明书压缩。
7. **提炼触发只看条数不看质量**——攒够 8 条就提炼，闲聊灌水也触发，可能提炼出低价值事实。

## 二、缓存命中率与 token 节省评估

### 2.1 现状

- **稳定前缀纪律（§零.9）**：每轮都变的内容一律不进 system prompt，唯一动态注入位是最后一条用户消息。联网搜索结果、记忆召回、动态清单、任务现状、当前时间全部走易变上下文（`OpenAiClient.kt:336 RUNTIME_CONTEXT_MARK`，注释明确论证"前缀逐字节相同→缓存照样命中"）。
- **cached_tokens 三种方言解析**：OpenAI/DeepSeek/Moonshot 的 `prompt_tokens_details.cached_tokens`、摊平在 usage 根的 `cached_tokens`、Anthropic 方言 `cache_read_input_tokens`；全 0 返回 null（"拿不到的不猜"）（`OpenAiClient.kt:56-67`）。
- **月度统计 + 命中率展示**：`UsageTracker.cacheHitRate / cacheHitLabel`，按自然月累计 total/prompt/cached 三数，跨月清零；数据页可见。

### 2.2 优点

这是**全项目最"懂行"的一块**。绝大多数开源 AI 聊天 App 根本不读 cached_tokens，更别提为命中率做稳定前缀工程。联网查询串贴末尾用户消息而非塞进 system（`ChatViewModel.kt:1019` 注释"留在前缀里等于每次搜索都把整段缓存作废一次"）这种细节，说明缓存是被当作一等公民设计的。

### 2.3 缺口

1. **分模型只记 total，不记 prompt/cached**（`SettingsRepository.addUsageTokensForModel` 签名只有 tokens）——`usage_by_model` 表算不出分模型命中率，而"哪个模型缓存友好"恰是选型最想知道的。
2. **记账盲区**：全项目 6 个记账点，**主动关心（ProactiveChat）和实时语音通话（PipelineVoiceCallEngine）都不记账**——而这两块恰恰是"看不见的自动消耗"，用户月底对账会低估实际用量。
3. **只有月累计，无逐次/分链路记录**——命中率是单月一个大数，看不出"哪类请求命中率低"（聊天 vs 提炼 vs 周报）。
4. **没有"节省金额"换算**——命中 token 在 DeepSeek 等服务商是半价甚至 1/10 价，用户看到的是"命中 X / Y"而不是"本月缓存省了约 ¥Z"，感知弱。
5. **前缀的隐性抖点**：档案增删、人设编辑会整体换前缀（低频用户动作，可接受）；但**记忆召回块命中不同条目时**，易变上下文长度变化会让历史截断点逐轮漂移——截断点漂移意味着老历史的前缀稳定性在"字数边界"上是逐轮变的，这部分无法被服务端缓存（属于方案固有代价，只能靠摘要压缩缓解，见记忆 §1.3-1）。

## 三、Live2D 评估（易用性 / 自定义 / UI 友好度）

### 3.1 总评：完成度与防御性一流，A 级

三层架构干净：UI（`ui/live2d`）→ `Live2dStage` 接口 → 引擎（`realtime/visual`）→ Cubism 官方 Framework。动作领域层（`com.menghuan.app.live2d`）纯 Kotlin 可 JVM 单测。

### 3.2 易用性

**优点：**
- 模型导入 4 步（会话设置 → 视频通话形象 → Live2D → 选 zip），staging 九步管线：ZipEntryGuard 拒绝对路径/`..`/盘符、GBK 条目名兼容国内打包工具、100MB/4000 条目/单条目 200MB 限额防 zip bomb、`Live2dPackageCheck` 校验 moc/贴图/物理引用；失败不留半成品、原绑定一字不改。
- 报错全是人话："没找到 .model3.json，请确认导出的是完整模型包"。
- 免费模型兼容：Groups/HitAreas 为空回退标准参数 ID + 几何包围盒命中兜底（实测"奶蛙"包）。

**缺点：**
- 文件选择器 mime 是 `*/*` 不过滤 zip；导入只有"正在解压"文案，**无进度反馈**，大包等待无感知。
- 通话动作绑定页**不能试播**（刻意取舍：设置页不养 GL 上下文），用户得去角色空间试，但页面上没有引导这句话。

### 3.3 自定义程度

**优点（非常充分）：**
- 动作四来源：内置 8 条 / 模型自带（onCatalogReady 同步）/ 用户拼装（ActionComposer：基础动作+强度+速度+时长+部位开关+表情）/ **AI 生成**（`AiActionGenerator`）。
- 双套绑定：通话四态绑定（idle/listening/thinking/speaking + 幅度四档）+ 点击互动三区绑定（头/身/其他，触碰还会翻成"摸了摸你的头"喂给 AI）。
- 舞台背景三档：预设渐变 / 相册图 / 视频（ExoPlayer + TextureView 静音循环，不引 media3-ui）。
- 归一化通道体系：轨道只认通用通道，加载时映射模型真实参数，缺通道降级跳过——任何模型都能演同一套动作，这是开源同类（Genuwin、DesktopFriends）完全没有的抽象。

**缺点：**
- **用户不能手动缩放/旋转角色**——旋转缩放只作为动作里的舞台通道存在，角色空间只有拖动位移（±0.6 屏），无 pinch-to-zoom。
- 无桌宠/悬浮窗形态（全仓只有无障碍 Agent 的停止按钮 overlay）；聊天页无任何 Live2D 展示。

### 3.4 UI 交互友好度

**优点：** 交互克制统一（无涟漪、长按菜单、单层弹层、无说明小字）；actionId=0 哨兵 + 删动作回收绑定，永不"绑到空气"；通话页右滑纯净态跟手；口型按播放头对齐 + 一阶低通帧率无关。
**缺点：** 核心文件巨大（`Live2dCharacter.kt` 42KB、`Live2dActionSheets.kt` 40KB），维护与新功能加入的理解成本在涨。

## 四、MCP 功能可行性评估

### 4.1 现状

全仓 `tool_call / function_call / "tools" / mcp` **零命中**。现有"AI 办事"能力两条路，都是自研文本协议：① 标记协议（记忆 `<add:>`、动态、表情 `[表情:名]`、语音条、想打电话）；② 无障碍 Agent（LLM 输出动作指令 → `ActionExecutor` 执行，白名单 + 敏感确认）。联网搜索也是 prompt 层拼结果，非 tool use。

### 4.2 可行性结论：**可行，且建议分两步走**

**前置条件（打通 tool calling 回环）**：`OpenAiClient` 目前只发 messages，要支持 OpenAI 兼容的 `tools` 参数 + 解析 `tool_calls` + 回灌 `role:tool` 结果。这是 MCP 和一切本地工具的共同地基。
⚠️ 风险：用户自配的 OpenAI 兼容端点未必支持 tools 字段——需要像 `ImageProbe` 那样做**能力探测 + 不支持就隐藏入口**（绝不能假设）。

**方案 A（推荐）：端侧 MCP 客户端**
- 官方 Kotlin SDK `io.modelcontextprotocol:kotlin-sdk`（JetBrains 合作维护，KMP 支持 Android，Maven Central）+ Ktor client（CIO 引擎）+ **Streamable HTTP 传输**。
- 只支持远程 MCP 服务器（HTTP/SSE/WebSocket）；**stdio 在 Android 上不适用**（不能 fork 子进程跑 npx），必须在 UI 上说清楚。
- 链路：MCP tools 清单 → 聚合成 OpenAI tools 参数 → 模型返回 tool_calls → 路由到对应 MCP server callTool → 结果回灌。
- 安全纪律（对标 2026 移动端 MCP 指南）：服务器白名单制（不许连任意地址）、高危工具调用前弹确认（elicitation 思路）、server token 走 Keystore（复用 `ApiKeyCipher` 模式）、工具结果按不可信内容处理（防 prompt injection）。

**方案 B：先做本地工具集（建议作为第一步）**
不接 MCP 协议，先用同一个 tool calling 回环暴露 App 自有能力：查/建任务、记账、查动态、读记忆、定闹钟。零外部依赖、风险最小，且能把回环工程（探测/解析/回灌/确认 UI）先打磨好。

**方案 C（不推荐）：BFF 云端转接**——本项目无服务端、用户自备 Key 的纯本地模式与"云端 MCP host"哲学冲突，且引入密钥出端风险。

**对标参考**：Genuwin（Android + Live2D）已做 Advanced Tool System（天气/搜索/Home Assistant）；AIRI 工具生态更丰富。MCP 是把这类能力标准化的最优路径。

### 5.1 梦欢的护城河（保持）
主动陪伴三件套、生活管理线、端侧 ASR 隐私模式、无障碍 Agent、Live2D 动作抽象层——任何一项单拿出来都不输，合起来没有对标物。

### 5.2 值得借鉴（按价值排序）
1. **DesktopFriends 的 function call 驱动表情/动作**——LLM 回复时直接调"表情列表/动作列表"，比现在的 `[表情:名]` 文本标记更稳（标记可能被模型写错格式）。可随 MCP 前置工程一起落地。
2. **Mem0 的 ADD-only 提炼 + hybrid 召回**——提炼不加 UPDATE/DELETE 状态机（与现有"按 key 覆盖"思路兼容），召回加向量信号（可选，用户自配 embeddings 端点）。
3. **Letta 的核心/归档分层**——对应到现有六态生命周期：core 永远注入、active 靠召回、archived 不注入但可查，现有模型已接近，缺的是**自动升降级**（久不访问的记忆自动降级）。
4. **AIRI 的内心独白/角色鲜活度设计**——与现有"心情状态/companionState"可互相印证。
5. **Genuwin 的智能家居工具**——印证 MCP 方向：用户自配端点 + 工具清单模式已被 Android 同类验证可行。

### 5.3 工程差距
- **无 CI**：仓库无 `.github/workflows`，597 项测试全靠手动跑。一个 `gradlew testDebugUnitTest` 的 GitHub Actions 就能兜底。
- **单模块无 DI**（手工 Service Locator）：当前规模可控，但 `MenghuanApp` 还在长胖。
- **AiPrompts 215 条 replace 链**：顺序敏感的考古层，靠测试断言兜底，是全项目最脆弱的单点。

## 六、风险与注意事项（施工纪律）

1. 一切交互/动效改动先问用户（项目铁律）。
2. 新功能先找 GitHub 成熟案例再动手（§零.1）——本报告各改进点均已附对标来源。
3. 功能入口/行为变化必须同版本同步 `AiPrompts` 手册 + `AiPromptsTest` 双断言。
4. 记忆/上下文改动必须守住稳定前缀纪律（§零.9）——任何"每轮都变"的内容不许进 system prompt。
5. Room 变更必须同步实体 indices/迁移/schema/迁移测试 + 反向验证（v0.74.0 血泪）。
6. 一批需求 = 一个版本号（两段式），做完才 +1。
