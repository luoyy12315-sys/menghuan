## 1. 背景与用户诉求

### 1.1 原始反馈

1. 「每次操作手机都要打开设置无障碍，然后容易卡还慢」
2. 「去 GitHub 上找找有什么解决方法或者新的 agent 方式」
3. 「哪种操作更便捷，更快速，代价更少」

### 1.2 诉求拆解

用户实际要的是**三个维度同时改善**：**便捷（用户动手少）× 快速 × 代价小**。

经过调研可以确认：**不存在单条路三维全赢**。三条维度指向的最优方案并不重合（详见 §4.4），所以本方案不是"选一条路"，而是**按性价比分层**——先把三个维度都不亏的部分做掉，再谈要不要吃下高代价高收益的部分。

### 2.2 当前主循环

`AgentLoop.run()` 是一个 `for (step in 1..config.maxSteps)`（默认 15 步），每步四件事：

1. **读屏** — `ScreenState.snapshot(rootInActiveWindow)`（`AgentLoop.kt:52`）
2. **决策** — `requestAction()` → `OpenAiClient.collectReply()`，非流式（`AgentLoop.kt:100-116`）
3. **执行** — `execute()` 分发 tap / text / swipe / back / home（`AgentLoop.kt:119-160`）
4. **等稳定** — `waitWindowStable()`（`AgentLoop.kt:163-177`）

**五个出口**：`done` / `sameActionStreak >= 2` / 步数用尽 / 白名单拒绝 / `isStopped()`。  
**一个重试**：`parseAction()` 返回 null → **原样重发一次**（`AgentLoop.kt:60-63`）。

## 3. 根因分析

### 3.1 痛点 A：为什么"每次都要去开无障碍"

**先纠正一个常见误解**：无障碍服务在正常情况下**重启后是会保留的**。会被关掉只有几种原因——App 被强行停止、国产 ROM 后台清理、服务崩溃后没人重挂、电池优化杀进程。

结合 §2.3 的实测（零前台服务、零恢复逻辑），可以判定：**用户每次去开，是因为服务被杀了而我们没有任何保活和自愈手段。**

**⚠️ 一个代码无法绕过的硬限制**：Android **不允许 App 自己重新打开无障碍服务**（安全限制）。所以保活只能"从源头减少被关"，真被关了之后只能靠**入口处一键深链跳转**兜底。

参考实现：DroidRun 的 `_recover_portal` —— 读状态连续失败 5 次后**自动重启无障碍服务**；外层 1s→10s 指数退避、7 次重试。我们完全没有对应物。

### 3.2 痛点 B：为什么"卡"且"慢"

**"卡"的两个来源**（都是代码问题，不是模型问题）：

- **W1 坐标定位**：快照与执行之间页面一旦变化，`findByCenter` 返回 null。这不只是"会失败"，它会**让整个循环变慢** —— 失败 → 多一次往返。
- **W2 失败不计入卡住判定**：一个反复失败的动作不会被 `sameActionStreak` 抓到，只能等模型自己认输调 `done`。这是**提示词兜底，不是代码兜底**。

**"慢"的真实账单**（跑满 15 步的估算）：

| 项目                       | 每步         | 15 步       | 性质      |
| ------------------------ | ---------- | ---------- | ------- |
| LLM 往返（网络 + 生成）          | 1–5s       | **15–75s** | 绝对大头    |
| `waitWindowStable` 无条件等待 | **≥900ms** | **≥13.5s** | **纯浪费** |
| 读屏 BFS                   | ~130ms     | ~2s        | 必要成本    |

### 3.3 关于「全量重发」的更正（重要）

本文档初稿曾把「每步把 40 条元素 + 8 步历史全量重发」列为最大延迟源，**这句一半是错的**：

- **8 步历史不是重发完整清单**。`history` 存的是 `execute()` 返回的**短描述串**（`"点击 [3] 保存"` / `"输入 [4] = xxx"`，见 `AgentLoop.kt:146,156`），8 条约 80 token，**不是大头**。
- **元素清单必须每步重发**。API 无状态，模型不看到当前屏幕就无法决策 —— 这是该层架构的**必然成本，不是浪费**。

**真正的病根是「步数 × 单次往返耗时」**，而不是"重发多少字"。因此优化方向应为：**减少往返次数** + **缩短单次往返**，而不是单纯"少发点内容"。

## 4. 行业调研（2026-10 现状）

### 4.1 无障碍摩擦的三种解法

| 方案                                                    | 重启后是否要重来        | 代价                                               |
| ----------------------------------------------------- | --------------- | ------------------------------------------------ |
| **自愈 + 保活**（前台服务 + 电池白名单 + 关闭时深链引导 + 读屏失败自动重挂）        | 不用，但依赖 ROM 不杀   | 纯本地，成本最低                                         |
| **Shizuku**（uid=2000 的 ADB 权限，无线调试激活，Android 11+ 免电脑） | **要重新激活**       | 生态最大（`awesome-shizuku` 收录大量同类）；需用户装一个 App        |
| **Dhizuku**（Device Owner 权限）                          | **不用，一次激活永久有效** | 激活时必须**删光手机所有账号 + 系统分身/双开**，OPPO 等需自行签名；支持的应用生态小 |

> ⚠️ **关键事实**：**Shizuku 也逃不过"重启要重激活"**。真正免掉这一步的只有 Dhizuku，但其一次性代价对普通用户过重。  
> **推论：对普通用户而言，"最小摩擦"靠自愈保活，不是靠装 Shizuku。**

佐证：Susu Phone Agent 的 README 明确写道 *"Accessibility services are heavily restricted on Android 13+"*；其技术选型说明也写明之所以用 Shizuku 而非无障碍，正是因为后者在 Android 13+ 限制严重。

### 4.2 观测层：树 / 视觉 / 混合

| 路线            | 代表                                   | 优势                       | 代价                           |

### 4.4 SOTA 规律与推论

1. **最强的不是纯视觉，也不是纯树，是混合**：AutoRPA（截图 + 树，Claude-sonnet-4.5）AndroidWorld **76.9**；mobile-use 84.5；DroidRun+AppCards 88.8。纯视觉的 Mobile-Agent-v3（GUI-Owl-32B）为 73.3。
2. **元素编号清单这个做法我们已经在用**（`[3] Button "保存"` 即 DroidRun 的 `indexed_formatter`）——**思路是对的，问题出在筛选与定位**。
3. **三个维度的最优不重合**：
   - 「便捷 + 代价低」最优 = **本地自愈保活类改动**（用户零操作、零新依赖）
   - 「快速」最优 = **动作脚本缓存**（重复任务从 15 次往返降到 0）
   - 两者**不冲突，可并行** → 这就是本方案的推荐组合
   - Shizuku 是「快 + 稳」的解，**但不是「便捷」的解**（摩擦形式变了，没消失）
   - 视觉模型在「代价」维度最差

## 5. 方案总览

Agent 可拆成**三层，每层可独立替换**：

```
观测层   无障碍树 BFS            →  截图 + 视觉模型 / 混合输入
决策层   每步一次请求            →  多步规划 · 动作脚本缓存
执行层   无障碍手势 dispatchGesture  →  Shizuku / ADB input 命令
（贯穿） 无保活，被杀即失效        →  前台服务 + 自愈 + 深链引导
```

本方案按**代价从低到高**分三批交付：

| 批次     | 内容                                      | 依赖                  | 是否需用户配合 |
| ------ | --------------------------------------- | ------------------- | ------- |
| **P0** | 保活自愈 / 等待时序 / 重试改写 / 元素瘦身 / 失败止损 / 定位稳定 | 无                   | **不需要** |
| **P1** | 动作脚本缓存 / Agent 专用模型配置                   | 无                   | 不需要     |
| **P2** | Shizuku 执行后端（可选）/ 观测层混合输入               | 需装 Shizuku / 需多模态模型 | **需要**  |

## 6. 详细改动清单

### 6.1 P0 —— 第一批（纯本地，不新增依赖）

#### A. 保活 + 自愈 + 一键深链（治痛点 A）

**问题**：零前台服务，服务被杀后无任何重挂手段。

**改法**：

1. 新增一个**前台服务**（`agent/AgentKeepAliveService`），在用户首次启用 Agent 后常驻，通知文案说明用途。⚠️ 需在 Manifest 声明 `foregroundServiceType` 并申请 `FOREGROUND_SERVICE` 权限（targetSdk 35 强制要求）。
2. `AgentAccessibilityService` 内加**恢复逻辑**（对应 DroidRun `_recover_portal`）：读屏失败连续 N 次后重置连接状态；`windowTick` 长时间无变化但操作未完成时视为异常。
3. 在 Agent 入口处检查 `isEnabledInSettings()`：为 false 时**一键深链** `Settings.ACTION_ACCESSIBILITY_SETTINGS`（省掉用户翻设置），并同时给**电池白名单**引导（国产 ROM 杀服务的主因）。

**风险**：常驻通知对部分用户是负担 → 做成"仅在使用过 Agent 后开启"，并提供关闭入口。

**验收**：连续使用 3 天，无需手动重开无障碍。

---

#### B. `waitWindowStable` 去掉无条件等待（治痛点 B-慢，**最快见效**）

**问题**：`AgentLoop.kt:163` 的 `quietStart` 从函数入口开始计时，逻辑上**保证最少等满 900ms**，15 步就是 ≥13.5 秒纯等待。

**改法**（三选一，倾向方案 2）：

1. 直接调低静默阈值 900ms → 500ms（改动最小，风险最低）
2. **先等"首次 tick 变化"最多 600ms；出现变化后再等静默 400ms；若 600ms 内完全无变化则直接返回**（"没有变化"本身就是稳定的证据）
3. 保留 900ms 但改成"tap 类动作才等，back/home/swipe 不等"

**风险**：⚠️ **属时序/行为改动** —— 慢 App 可能变化延迟 >600ms，提前返回会读到旧界面。**需用户确认后再动。**

**验收**：单步等待时间从固定 900ms 降至 200–500ms；任务成功率不下降。

---

#### C. 重试不再"原样重发"（治痛点 B-慢 + 省钱，**W4**）

**问题**：`AgentLoop.kt:60-63` 解析失败后的重试，发的是与第一次**完全相同**的请求 —— 同一输入必然得到同一错误答案，等于花两次钱买同一个错。

**改法**：`requestAction()` 增加一个 `retryHint: String = ""` 参数；重试时把它追加到 user prompt 尾部（例如「上一次的输出无法解析。只输出一个 JSON，不要任何其他文字。」）。

**风险**：低。

**验收**：单元测试断言重试请求与首次请求**不相等**。

---

#### D. 元素清单瘦身（治痛点 B-慢 + 省钱）

**问题**：`ScreenState.kt:42` 的准入条件是 `clickable || editable || scrollable || hasText` —— **`hasText` 会把纯文本装饰节点全部放进来**（标题、价格、说明文字），40 条里可能一半是模型永远不会点的。

**改法**（对应 DroidRun 的 `ConciseFilter`）：

1. 收紧准入：默认只收 `clickable || editable`；`scrollable` 单独标注；**纯文本节点仅在屏幕上没有任何可交互元素时**才作为兜底发出（避免模型无处可点）。
2. **去重**：内容完全相同（`type + label`）的节点，保留前 3 个并标注 `×N`。
3. `text` / `contentDesc` 截断 30 → 20 字（**注意**：截断只影响给模型看的清单，不影响 `UiElement` 内部值）。
4. 考虑剔除键盘节点（输入法包名），减少干扰。

**风险**：⚠️ 收得太紧会让模型看不到关键文本（例如只有文字描述的按钮）。**建议保留兜底逻辑**，并在真机上对比成功率。

**验收**：清单条数平均下降；单步输入 token 下降；任务成功率不下降。

---

#### E. 失败动作也计入"卡住"判定（治痛点 B-卡，**W2**）

**问题**：`AgentLoop.kt:76` 的 `sameActionStreak` **只在动作成功时比较**，反复失败的动作永远不会触发"卡住"。

**改法**：

- 把 `history += "动作 X 执行失败"` 也纳入 streak 比较（按"动作签名"而非"执行结果描述"比较）；
- 连续同类失败 2 次 → 直接中止并回报，而不是继续烧往返等待提示词兜底。

**风险**：低。注意别把"tap 两次不同元素"误判成同类。


**验收**：构造"反复点击不存在的元素"场景，第 3 步内中止。

---

#### F. 定位稳定化（治痛点 B-卡，**W1**）

**问题**：`ActionExecutor.findByCenter` 用快照时的 `centerX/Y` 回找节点，页面一变即失效。

**改法**：
1. 优先用 **`viewIdResourceName`（resourceId）** 定位，坐标降级为兜底。
2. 给每次 `snapshot()` 打**时间戳/序号**，执行前校验；不一致则不执行并回报"界面已变化"。
3. 元素编号与快照绑定，禁止跨快照复用编号。

**风险**：低-中（resourceId 在部分 App 里为空，必须保留坐标兜底）。

**验收**：W1 复现场景下失败率下降。

---

#### G. 敏感词围栏补齐（**W3**，安全项，建议同步做）

**问题**：`isSensitive()` 只查元素文案，`text` 动作要**输入**的 `value` 不参与检查。

**改法**：`AgentLoop.kt:151-154` 的 `text` 分支，除 `isSensitive(element)` 外，还要判 `action.value` 是否命中敏感词表。

**风险**：极低。

**验收**：单测覆盖「在备注框里输入含敏感词的文本 → 触发确认」。

---

### 6.2 P1 —— 第二批（纯本地）

#### H. 动作脚本缓存（治痛点 B-慢的**根本**）

**思路**：第一次执行某任务时，把「动作序列 + 每步的元素指纹」存成本地脚本；下次遇到**相同目标 + 相同起始界面指纹**时，直接重放，不再逐次问模型。

**关键设计**：
- 指纹用 `包名 + 元素 resourceId 序列` 而非坐标；
- 每一步重放前做**匹配校验**，不匹配立即回退到"问模型"模式；
- 脚本按成功任务存储，失败任务不落盘；
- 提供"清除已学脚本"入口。

**收益**：重复任务从 15 次 LLM 往返 → **0 次**（对应 §0 图里的 2–5 秒）。

**风险**：界面改版后脚本失效 → 必须靠匹配校验兜底，**不允许"盲重放"**。

---

#### I. Agent 专用模型配置项

**思路**：每步决策是"这一屏该点哪个"的简单任务，用小/快模型足够。新增一个 `agent_model` 配置，默认跟随全局，允许单独指定。

**收益**：延迟可能近半。**风险**：低（仅新增配置项，不影响现有链路）。

---

#### J. 前缀缓存优化（**先测再改**）

**现状**：`AgentPrompts.userPrompt()`（`AgentPrompts.kt:55`）顺序是「目标 → 屏幕 → 历史」。而**屏幕清单是整体替换的、历史是追加式增长的** → 把**历史提到屏幕之前**，两次请求的公共前缀可从"当前屏幕元素："延伸到**整段历史**。

**⚠️ 前置判据**：先看用量页里 Agent 这条链的 `cachedPromptTokens` 是不是 0。
- 服务商是 **OpenAI 那种 1024 token 一块**的自动缓存 → 我们的 `SYSTEM` 只有约 175 token，**够不到门槛**，改顺序也白搭；
- 服务商是 **DeepSeek 的 64 token 粒度** → 吃得到。

**结论**：**先读数据，再决定改不改。** 不要盲改。

---

### 6.3 P2 —— 第三批（范式变化，需用户配合）

#### K. Shizuku 执行后端（可选）

**定位**：**不是"便捷解"**，而是"**执行更快更稳** + 为视觉铺路"。
- 用 `input tap/swipe/keyevent` 替代 `dispatchGesture`（Susu 项目实证 *"Commands like input keyevent, dumpsys window, and monkey work reliably"*）；
- 用 `screencap` 拿截图，绕开 API 30 限制。

**改法**：抽象出执行后端接口，实现「无障碍 / Shizuku」双后端，用户在设置里选。参照 `Turbo1123/roubao`、`wuwei-crg/LXB-Framework`、`zairyo/Susu` 的接入方式。

**风险**：用户需安装 Shizuku；**每次手机重启后需重新激活**；引入 aar 依赖。

---

#### L. 观测层换混合输入（截图 + 树）

**前置问题（必须先回答）**：**用户配置的 API 是否支持多模态（传图）？**
- **支持** → 客户端侧已经铺好了：`OpenAiClient.collectReply(..., imageDataUrl)` 参数已存在，且 `util/LedgerImageRecognizer.kt` 已在生产使用这条通道。**工程量比预想小得多。**
- **不支持** → 只能内置端侧模型（GUI-Owl-1.5-2B / UI-TARS-2B）。**这一项工程量确实大**（模型转换、打包、内存、仅 arm64），但**我们的构建本来就已具备一半条件**：`ndk.abiFilters` 仅 `arm64-v8a`、`noCompress` 含 `onnx`、sherpa JNI keep 规则已就位。

**⚠️ 硬约束**：`minSdk = 26`，而 `AccessibilityService.takeScreenshot()` 需 **API 30**。API 26–29 设备走不了无障碍截图（除非引入 MediaProjection，但那需要每次会话用户授权，对 Agent 场景不可接受）→ **视觉路线应作为"API 30+ 增强"，而非唯一路径。**

## 7. 实施顺序与里程碑

```
M1（P0 前半）  保活自愈 + 等待时序 + 重试改写      → 用户可感知：不用再手开无障碍、明显变快
M2（P0 后半）  元素瘦身 + 失败止损 + 定位稳定 + 敏感补齐 → 用户可感知：不再卡死
M3（P1）       动作脚本缓存 + Agent 专用模型        → 用户可感知：第二次做同一件事几乎瞬间完成
M4（P2，待定） Shizuku 后端 / 观测层混合输入        → 需先确认前置条件
```

**每批做完即停，交付给用户验证后再进入下一批。** 不一次性铺开。

## 8. 风险、回滚与边界

### 8.1 主要风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| B 项（等待时序）提前返回读到旧界面 | **中** | 保留 2.5s 上限；先在真机对比成功率再合入；**改动前必须经用户确认** |
| D 项（元素瘦身）收得过紧，模型看不到关键元素 | 中 | 保留"无可交互元素时发纯文本"的兜底；真机 A/B 对比 |
| A 项（前台服务）常驻通知骚扰 | 低-中 | 仅在使用过 Agent 后开启 + 提供关闭入口 |
| H 项（脚本缓存）界面改版后脚本失效误操作 | **中** | 强制匹配校验；不匹配即回退问模型；**禁止盲重放** |
| L 项（视觉）截图含其他 App 隐私内容 | 中 | 复用现有白名单围栏；在 UI 上明示"屏幕文字会发送到你自己配置的接口" |

### 8.2 回滚

- P0 全部为**本地改动 + 新增文件**，逐条可独立回退；
- B 项改的是阈值与判定逻辑 → 保留原常量，出问题改回一个数即可；
- 不建议用 `git checkout -- <文件>`（工作区长期存在大量未提交改动，历史上曾冲掉 `manualPatch` 链）。

### 8.3 明确不做的事

- **不引入 Dhizuku**（激活需清空账号与系统分身，对普通用户不可接受）。
- **不把 Shizuku 做成强制依赖** —— 只能作为可选后端。
- **不做纯视觉单路径** —— `minSdk = 26` 决定了它只能是增强项。
- **不改流式** —— 流式**不能减少总时长**（JSON 必须完整才能解析执行），只改善"看得见在动"，不列入本方案的提速手段。
- **不动键盘 / 语音模块**（项目铁律）。

## 9. 验收标准

1. **痛点 A**：连续使用 3 天，无需手动重新开启无障碍；真被关闭时，入口处一键可达设置页。
2. **痛点 B-慢**：单步固定等待从 ≥900ms 降到 200–500ms；单步输入 token 明显下降；任务成功率**不下降**。
3. **痛点 B-卡**：W1/W2 场景下，3 步内中止而不是烧完 15 步。
4. **重复任务**：同一任务第二次执行，模型调用次数为 0（走脚本缓存）。
5. **安全**：W3 场景被拦截；白名单围栏行为不变。
6. **回归**：现有 Agent 相关测试全绿；不破坏 `manualPatch` 链与 `AiPromptsTest`。
