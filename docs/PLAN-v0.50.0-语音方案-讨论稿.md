# 梦欢 语音栈方案（v0.50.0 · 讨论稿）

> 更新 2026-10-04（第二轮拍板）：用户拍板「删掉喇叭/朗读」「去掉 v7a 省体积」；
> 并指出「梦欢语音方案越搞越乱，想推倒重来」，要求**先参考爱语（爱语 2.9.5）的实现**。
>
> **识别最终拍板「方案甲 + 零内置模型」**：
> - 识别改用**离线高精度模型 SenseVoice**（非流式，~230MB int8），**通话与语音消息共用同一个**；
> - **APK 不内置任何识别模型**——装完后提示用户联网下载；
> - **删除「纯离线 / 单机」定位**：梦欢允许联网运行。
>
> 本文只做方案与讨论，**不含任何代码改动**。
> 证据来源：爱语 `classes.dex` 反编译字符串、`爱语_2.9.5.apk` 的 assets 清单、爱语官方使用协议（assets/1.txt、2.txt）、`音色/` 样本文件夹。

---

## 0. 结论先行

梦欢的「乱」，乱在两件事：
1. **堆了三套语音机制**：流式小模型（识别主力）+ 三级级联（云端 Whisper / 系统识别器兜底）+ 通话管道（另起一套）。其中**级联的后两级实测永远走不通**，却还挂在链路上。
2. **两个 TTS 概念**：Edge TTS 朗读 + 通话自己的 TTS，互不相干。

爱语反而简单，就三句话：
- **识别只走端侧 sherpa-onnx（模型可选）**，不碰云端 ASR；
- **合成只走云端 TTS（默认硅基流动 CosyVoice2，支持音色克隆）**；
- **AI 用 `【语音条】` 标记自主决定发不发语音**，配三个独立开关。

**建议**：对齐爱语，把梦欢语音栈收敛成「**一条识别链 + 一条合成链 + 一个标记协议**」；
识别模型**不内置、按需下载**，让 APK 保持轻量。

## 1. 爱语是怎么实现的（拆解 + 证据）

### 1.1 语音识别：端侧 sherpa-onnx，内置一个大流式模型 + 可选下载

| 证据 | 说明 |
|---|---|
| dex 里**没有任何 `/audio/transcriptions`** | 不用云端 ASR（梦欢的云端 Whisper 兜底在爱语这儿压根不存在） |
| dex 引入 `github.com/k2-fsa/sherpa-onnx` | 端侧识别引擎 |
| `爱语_2.9.5.apk` 的 assets **只内置一个识别模型**：`encoder-epoch-20-avg-1-chunk-16-left-128.int8.onnx`（64.8MB）+ `decoder-…onnx`（4.9MB）+ `joiner-…int8.onnx`（1MB）+ `bpe.model` + `tokens.txt`，**合计约 71MB** | 一个**大流式 zipformer（transducer）**，即默认「听觉模型」 |
| dex 出现大量 sherpa 模型名（`paraformer-zh-small`、`sense-voice-…`、`whisper-base`、各类 `zipformer-*`）+「选择模型 / 搜索模型 / 听觉模型测试 / 自定义模型路径」 | **可下载的模型目录**（不随包），用户按需切换 |
| 官方协议 3.1.3：「录音权限仅用于实现语音转文字回复功能，**全程不录制、不存储任何音频数据**」 | **直接从麦克风流式识别**，音频不落盘 |

> 关键结论：爱语**不是固定一个模型**，而是「内置一个大流式模型当默认 + 可选下载更强的离线模型」。
> 它准的核心原因是**模型够大**（~71MB，是梦欢 14M / 25MB 的数倍），不是黑科技。
>
> 关键差异：爱语**不存用户音频**，所以能用流式；梦欢要落"语音条"所以得录下来。

### 1.2 语音合成：云端 TTS，默认硅基流动 CosyVoice2，支持音色克隆

| 证据 | 说明 |
|---|---|
| `POST https://api.siliconflow.cn/v1/audio/speech` | 硅基流动 TTS |
| dex 字符串 `CosyVoice2-0.5B` | 默认模型 |
| dex：「音频克隆 — 上传音频样本克隆音色」「正在截取前 15 秒音频…」「voiceclone 音频样本超过 10MB 限制」 | **音色克隆**：上传样本 → 自动截前 15 秒 → ≤10MB → 克隆 |
| `音色/` 文件夹里全是 MP3 样本（Cartethyia.mp3、Changli.mp3…） | 就是克隆用的素材 |
| `https://api.xiaomimimo.com/...` + 「MiMo 响应里取不到音频数据」 | 也支持**小米 MiMo**（响应里直接带音频） |
| `https://api.xxx.com/v1/audio/speech` | 还支持**自定义 TTS 端点** |
| dex：「音频Base64大小:」「TTS 音频获取失败」 | 音频以 base64 回传 |

### 1.3 AI 语音条：标记协议 + 三个独立开关

| 证据 | 说明 |
|---|---|
| dex 字符串 **`【语音条】`** | **AI 用标记自主决定发语音**（与梦欢 `[生图:…]` 同族思路） |
| dex：「语音条 — 生成语音以气泡展示，点击播放」 | 语音条 = 合成语音 + 气泡，**不是**朗读 |
| dex：「语音朗读 — 自动朗读 AI 回复」 | 朗读是**另一个独立功能** |
| dex：「语音通话」 | 通话是**第三个独立功能** |
| dex：「语音条始终显示文字」「语音条与文字自动去重」「收到语音条时自动播放」 | 三个配套细节开关 |
| dex：「语音消息已自带文字转写:」「语音转文字结果:」 | 语音消息**自带转写文本**随消息保存 |

**爱语的语音设置 = 三个开关 + 三个细节项**：
```
语音朗读（自动朗读 AI 回复）
语音条（生成语音以气泡展示，点击播放）
  ├ 语音条始终显示文字
  ├ 语音条与文字自动去重
  └ 收到语音条时自动播放
语音通话
```

### 1.4 语音通话：独立模式

- dex：「语音通话指令」「语音通话。请立即以自然、热情或期待的开场白开始对话。」
  → 有专门的通话提示词与开场逻辑

## 2. 梦欢现状诊断：乱在哪

| # | 乱点 | 具体 |
|---|---|---|
| 1 | **识别堆了三套** | 流式 14M 小模型（主力）→ 云端 Whisper（端点不支持，永远空）→ 系统识别器（国产 ROM 文件输入不生效）。后两级是**纯历史包袱** |
| 2 | **模型又小又选错形态** | 用的 `streaming-zipformer-zh-14M` 只有 14M 参数（~25MB），官方定性「准确率不佳」；而且梦欢是**"录完再识别"**，本就该用**离线非流式**模型，用流式是选错了工具——**语音消息和通话两头都不准** |
| 3 | **TTS 两个概念** | Edge TTS（微软非官方免费端点，易失效）+ 通话自己的一套 TTS |
| 4 | **通话另起一套** | `PipelineVoiceCallEngine`（VAD+ASR+LLM+TTS+播放）与语音消息链路**零共享** |
| 5 | **模型被两处共用** | `SherpaAsr`（语音消息）与 `CallAsr`（通话）共用同一套 `asr/` 文件——方案甲下**有意共用**，换模型时一处替换、两处生效 |
| 6 | **朗读与语音条会重复** | v0.49.0 的"每条朗读"和"AI 自主发语音条"是两回事（用户已决定**删掉朗读**） |

## 3. 目标架构（推倒重来后长什么样）

```
用户语音  ──►  SherpaAsr（端侧 · SenseVoice 离线模型 · 去掉无效级联）
AI 通话   ──►  CallAsr（同一个 SenseVoice · 按 VAD 分段识别）
AI 回复   ──►  【语音条】标记判断 ──► TtsClient 合成 ──► 语音气泡（可长按转文字）
```

- **一条识别链**：只留端侧 sherpa-onnx，**通话与语音消息共用同一个 SenseVoice 离线模型**；删掉云端 Whisper 与系统识别器兜底
- **模型不内置**：APK 不带识别模型，装完后提示下载（见第 4 节）
- **一条合成链**：统一 `TtsClient` 抽象，底层可切 硅基流动 / 小米 MiMo / 自定义端点
- **一个标记协议**：`【语音条】`（与 `[生图:…]`、`[操作手机:…]` 同族）
- **三个开关**（对齐爱语）：语音条 / 语音通话（朗读已删）
- **一个音色体系**：人设 → 音色（现成音色 or 克隆音色）

## 4. 识别模型与下载设计（本轮新增，核心）

### 4.1 选型：SenseVoice（离线非流式）

| 项 | 值 |
|---|---|
| 模型 | `sherpa-onnx-sense-voice-zh-en-ja-ko-yue`（int8，**~230MB 级**，实施前实测） |
| 形态 | **离线 / 非流式**（一次吃完整段音频，准确率高于流式） |
| 语言 | 中 / 英 / 日 / 韩 / 粤 五语言 |
| 中文准确率 | 约 **8% CER**（优于 Paraformer-zh 的 ~9.8%） |
| 附加能力 | **情感检测**（开心/难过/生气/中性）+ **音频事件**（笑声/掌声/背景乐等），一次推理顺带给出，不额外耗时 |
| 为什么选它 | 在"能塞进手机的体积"里，它是中文准确率最好的一档；更 SOTA 的 FireRedASR2 / xlarge zipformer 都 **700MB+**，不现实 |

### 4.2 零内置 + 装后下载

**决策：APK 不打包任何识别模型。**

- **触发时机**：首次点击「语音输入」或「通话」时提示下载（**不是**装完一启动就弹，避免像流氓软件）
- **下载源（三保险）**：
  1. `hf-mirror.com`（HuggingFace 国内镜像，**默认，快**）
  2. GitHub Releases（官方托管，**备用**）
  3. **手动导入**（文件选择器，用户自备模型文件）
- **下载能力**：断点续传 + sha256 校验 + 进度显示 + 可暂停/重试
- **落盘位置**：`filesDir/asr/`（sherpa-onnx 支持从文件路径加载，不要求必须在 assets）

### 4.3 无模型时的降级

- **文字聊天照常**（核心功能不受影响）；
- 语音输入 / 通话 → 明确提示"需先下载语音模型"并给下载入口，**不静默失败**。

### 4.4 体积收益

| 动作 | 省下 | APK 结果 |
|---|---|---|
| 现状（v0.49.0） | — | 80.85 MB |
| 去掉内置模型（`assets/asr/` 约 26MB） | −26 MB | ~55 MB |
| 再去掉 `armeabi-v7a` | −21 MB | **~34 MB** |

### 4.5 通话字幕形态（重要变化）

用离线模型后，通话**不再有"逐字实时"字幕**：
- **简单做法**：每个 VAD 分段说完 → 离线识别 → 字幕整段出现；
- **进阶做法**：用 sherpa-onnx 官方 **simulated streaming**（拿离线模型在增长的音频缓冲上反复重跑）→ 可近似实时，代价是重复计算。

> 用户已拍板接受「方案甲」的字幕形态（说完一段才出）；simulated streaming 作为后续可选增强。

## 5. 迁移路径（建议分步，降低返工风险）

> AGENTS.md §零.2 / §零.4：语音模块已返工多轮，**禁止试错式连改**。分步走、每步可验证。

| 步 | 内容 | 收益 / 风险 |
|---|---|---|
| 1 | 识别换 **SenseVoice 离线模型**（通话 + 语音消息共用）；砍掉云端 / 系统两级兜底；**APK 去掉内置模型**，新增下载链路（hf-mirror → GitHub → 手动导入） | 收益最大、风险最低 |
| 2 | TTS 抽象化，接入**硅基流动 CosyVoice2 + 小米 MiMo + 自定义端点**（三家第一版一起做，含音色克隆） | 中等，涉及网络与费用 |
| 3 | AI **`【语音条】`** 标记协议 + 开关；**删掉朗读** | 中等，UI + 落库 |
| 4 | **通话并入同一 TTS 抽象**（本轮做）：通话切云端 TTS，保留 VAD 分段 + 字幕 + barge-in | 高，动通话核心 |
| 5 | 去掉 v7a（省体积） | 低 |

> **第 1 步模型落地前先实测**：确认 SenseVoice 的实际体积、中文准确率、单段识别耗时（尤其通话每段的延迟），再定。

## 8. 风险清单

| # | 风险 | 应对 |
|---|---|---|
| 1 | Edge TTS 是微软非官方端点，可能被墙 / 失效 | 换官方付费 TTS（硅基流动 / 小米） |
| 2 | 云端 TTS 要花钱 | 用户自备 Key；或选限时免费的小米 MiMo |
| 3 | 音色克隆涉及音频上传 | 需用户知情；样本 ≤10MB、截前 15 秒 |
| 4 | 模型下载依赖网络（首次用语音要联网） | 三源兜底（hf-mirror / GitHub / 手动导入）+ 断点续传；文字功能不受影响 |
| 5 | 模型下载失败 / 文件损坏 | sha256 校验 + 可重试 + 手动导入 |
| 6 | 通话改用离线模型后，字幕不再是"逐字实时" | 用户已接受（方案甲）；后续可选 simulated streaming 增强 |
| 7 | 通话每段识别引入延迟（离线模型比小流式慢） | 实测单段耗时；必要时缩短 VAD 分段 |
| 8 | 通话切云端 TTS 后每句多一次网络往返（延迟略增） | 交互形态不变（本就是对讲机式）；先播字幕兜底，音频后到 |
| 9 | 用户未配 TTS Key 时通话 / 语音条无声 | 明确提示 + 字幕兜底（已拍板第 9 条） |
| 10 | 一次重写风险高 | 按第 5 节分步，每步真机验证 |
